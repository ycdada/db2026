# 新未来优化方向

本文档综合 `todolists/未来优化方向.md`、`todolists/性能测试.txt`、`todolists/性能测试修复对话恢复记录.md`、题目文档、`todolists/火焰图输出.md` 以及当前代码状态，按“预期性能收益从大到小”排列后续可推进的新优化方向。

排序说明：

- 这里的“收益”主要指 TPC-C 性能测试阶段的吞吐量提升潜力，其次兼顾 load、恢复时间和本地调试效率。
- 已经采用的优化不重复列为新方向，例如复合索引、最长前缀索引选择、索引上下界、Buffer Pool 分片、Lock Manager 分片、表记录内存化缓存等。
- 所有优化必须保持通用机制属性，禁止针对固定 TPC-C 表名、字段结构或 SQL 文本硬编码。
- 高收益不等于优先立即实现；事务、WAL、MVCC、索引生命周期相关优化必须先有本地一致性保护和回归测试。

## 1. 性能构建配置切换到 Release/O2 或 O3

实施状态：已完成。根目录 `CMakeLists.txt` 已默认使用 `Release` 构建，Release 使用 `-O3 -DNDEBUG`；Debug 仍保留 `-O0 -g -ggdb3`，`RelWithDebInfo` 用于带符号信息的优化构建和火焰图采样。

预期收益：极大。

证据与背景：

- 优化前根目录 `CMakeLists.txt` 全局使用 `-Wall -O0 -g -ggdb3`。
- 火焰图中出现大量 STL、`shared_ptr`、parser/AST 构造析构和 `Page::Page()` 开销；在 `-O0` 下这些成本会被明显放大。

建议方向：

- 保留 Debug 构建用于本地排错，同时使用明确的 Release/RelWithDebInfo 构建方式。
- 性能提交前使用 `Release`；后续可继续评估 `-flto` 的收益和风险。
- 不要把 profiling 专用 `-pg` 混入正式性能构建。

正确性风险：

- 中等。需要完整跑 `unit_test`、`ctest`、`q9_repro`、简化 TPC-C invariant stress，防止未初始化内存或 UB 在优化编译下暴露。

## 2. WAL 批量刷盘、group commit 与异步日志落盘

实施状态：已完成第一阶段 group commit。提交/回滚路径现在等待自身 commit/abort LSN 持久化；`LogManager` 会把当前 log buffer 复制为本地刷盘批次，释放缓冲区锁执行一次磁盘写入，并唤醒所有目标 LSN 已覆盖的等待事务。后台异步日志线程、log buffer 环形化和更完整 crash recovery 压测仍作为后续阶段。

预期收益：极大。

证据与背景：

- 性能测试是写密集短事务，NewOrder、Payment、Delivery 都频繁提交。
- 赛题优化建议明确提到日志管理器线程池和异步刷盘。
- `性能测试修复对话恢复记录.md` 表明此前 Phase 3 一致性失败重点与 aborted partial writes、跨表原子性、恢复正确性相关，说明日志优化必须非常谨慎。

建议方向：

- 已先做 group commit：多个事务可共享一次 flush，保证 WAL 顺序和 commit 持久性。
- 再评估后台日志刷盘线程，提交路径只等待本事务 commit LSN 已持久化。
- 对 log buffer、log record 采用池化或环形缓冲，减少短事务分配。

正确性风险：

- 很高。必须保持先写日志后写数据、commit 持久化、abort undo、crash recovery 和 checkpoint 语义。
- 每次继续推进异步线程或 log buffer 结构调整时，都应跑题目十恢复用例、kill -9 后重启检查，以及 TPC-C invariant stress。

## 3. 通用 SQL 解析/分析/计划缓存

预期收益：很大。

证据与背景：

- 火焰图显示 `yyparse()`、`yylex()`、`ast::SemValue` 构造析构、`shared_ptr` 释放占比明显。
- TPC-C workload 通常由少量模板化 SQL 反复执行，只是常量不同。

建议方向：

- 做通用 statement cache 或 plan cache，按规范化 SQL 结构缓存 parse/analyze/plan 结果。
- 常量作为参数绑定或轻量替换，不把固定 SQL 文本写死到执行路径。
- 缓存需要带 schema version；DDL、create/drop index、load、checkpoint 等会改变元数据的操作必须使相关缓存失效。

正确性风险：

- 中高。需要确保列类型、索引选择、事务隔离级别、session knob、output format 不被错误复用。

## 4. 简单 DML/点查路径的通用快速执行器

预期收益：很大。

证据与背景：

- TPC-C 主事务包含大量主键/复合键点查、点更新和插入。
- 当前系统已经能选择复合索引和索引上下界，但每条语句仍会走完整 parser、analyze、plan、portal、executor 链。

建议方向：

- 在 plan 已确定为单表、索引前缀点查、简单谓词、简单 set/insert 时，走通用 fast executor。
- fast executor 仍从 planner 产物进入，不直接匹配固定 SQL 文本。
- 将表达式求值、条件重检、索引维护、MVCC 写冲突、日志记录整合为更少的虚调用和对象分配。

正确性风险：

- 高。必须保留 UPDATE/DELETE 的 visible record 重读、predicate recheck、写写冲突、abort rollback 和索引一致性。

## 5. 索引并发度与 B+Tree 热路径优化

预期收益：大。

证据与背景：

- 性能测试文档强调提高索引并发度。
- 当前 TPC-C 访问路径高度依赖复合索引；Lock Manager 和 Buffer Pool 已经分片，索引本身可能成为下一层竞争点。

建议方向：

- 引入更细粒度的 B+Tree latch coupling 或乐观读路径，减少全索引/页面级长时间持锁。
- 优化 `lower_bound`/`upper_bound` 到叶子扫描的常见点查路径。
- 对只读点查支持更轻量的 latch 范围，写路径保持分裂、合并、回滚安全。

正确性风险：

- 高。需要索引一致性测试、并发插入/删除/更新测试、crash recovery 后索引与 heap 对齐检查。

## 6. 索引叶子保存稳定记录槽句柄或记录指针

预期收益：大。

证据与背景：

- 现有文档指出参考项目中存在“索引保存记录指针”，当前项目未采用。
- 当前索引保存 `Rid`，命中后仍要通过记录文件句柄读取内存化记录副本。

建议方向：

- 评估索引叶子保存稳定 record slot handle，或保存可校验的记录缓存指针。
- 指针必须能处理更新、删除、回滚、GC、close/reopen、destroy/recreate、recovery 后重建。
- 可先只做“句柄层”而非裸指针：索引返回 `Rid + generation/version`，记录缓存验证后零拷贝返回。

正确性风险：

- 很高。`record_manager_regression_notes.md` 已说明共享记录缓存生命周期容易出错，不能靠删除缓存优化来规避。

## 7. 扩大批处理执行，但优先只读 SELECT 和索引范围扫描

预期收益：中到大。

证据与背景：

- 现有文档说明 `SELECT` 已重新启用 `NextBatch`，DML 仍保持单行执行以保护一致性。
- 火焰图中 `RmFileHandle::snapshot_rids()` 出现，说明扫描类路径仍有批量优化空间。

建议方向：

- 先优化只读 SELECT 的批内条件判断、投影、排序和聚合。
- 对 IndexScan 的连续范围读取提供批量接口，减少每条记录一次函数调用和对象分配。
- DML 批处理暂缓；除非先建立强一致性测试，否则不要把 UPDATE/DELETE 批量化。

正确性风险：

- 中。只读路径风险较低，但 SI/SER 下仍要保证事务级快照一致。

## 8. 优化 `RmFileHandle::snapshot_rids()` 和扫描快照构造

预期收益：中到大。

证据与背景：

- 火焰图中 `RmFileHandle::snapshot_rids() const` 进入热点。
- 当前 `RmScan` 构造时会快照 Rid 集合，短查询和重复扫描可能反复构造临时 vector。

建议方向：

- 为只读稳定表状态维护增量 Rid snapshot 或 generation cache。
- 对短事务顺序扫描使用轻量 cursor，避免每次扫描都复制完整 Rid 列表。
- 对 MVCC/SER 谓词读保留必要的读集记录，不能因为跳过 snapshot 而漏掉范围读依赖。

正确性风险：

- 中高。需要覆盖 delete tombstone、GC、abort insert rollback、recreate file cache lifecycle。

## 9. 页面对象初始化和 Buffer Pool 启动/恢复成本优化

预期收益：中等；对恢复时间可能较大。

证据与背景：

- 火焰图顶部为 `Page::Page()`，`Page` 构造会 `reset_memory()`，同时 `char data_[PAGE_SIZE] = {}` 也会清零。
- `BUFFER_POOL_SIZE = 65536`，一次初始化会触碰约 256MB 页面内存。

建议方向：

- 去除重复清零，只在 frame 首次分配或页面置换时必要清理。
- 评估懒初始化 buffer frame，避免 server 启动和恢复阶段一次性清零整个 buffer pool。
- 对恢复测试，减少启动到可服务时间尤其重要。

正确性风险：

- 中。任何懒清零都必须保证新页、删除页、重用 frame 不泄露旧数据。

## 10. 事务、锁、日志、执行器对象池化

预期收益：中等。

证据与背景：

- 已有事务对象池只保守复用隐式只读事务。
- 火焰图中大量 STL 分配、`shared_ptr` 释放、`Condition`、`ColMeta`、AST 节点构造析构可见。

建议方向：

- 增加线程本地小对象池：`LockRequest`、`WriteRecord`、log record buffer、执行器临时 `RmRecord`、条件向量等。
- 池化对象必须带 reset/poison 检查，避免事务状态串扰。
- MVCC、显式事务、SER 事务的状态对象暂不激进复用。

正确性风险：

- 中高。此前事务对象池已经暴露过生命周期风险，必须继续保守。

## 11. MVCC 版本链和 GC 成本优化

预期收益：中等。

证据与背景：

- 性能测试在快照隔离基础上进行。
- 已有修复包括 visible read overload、watermark 后清理 committed delete tombstone、写路径重读和谓词重检。

建议方向：

- 缩短可见性判断路径：按表或记录维护最新提交版本快速入口。
- GC 分批后台执行，避免在前台事务提交或读路径中集中清理。
- 对短事务热点记录减少版本链遍历。

正确性风险：

- 高。不能破坏旧快照读、自写可见、写写冲突和 abort 清理。

## 12. 热表/热索引常驻与 Buffer Pool 策略微调

预期收益：中等。

证据与背景：

- TPC-C 热点集中在 warehouse、district、stock、customer、orders、new_orders、order_line 的主访问路径。
- 当前已有聚簇化记录布局和 Buffer Pool 分片，但替换策略仍偏通用 LRU。

建议方向：

- 做通用 buffer-resident fast path，例如按访问频率保护热页，而不是固定表名常驻。
- 评估 LRU-K、CLOCK-Pro 或冷热分区，避免短期扫描污染热点页。
- 对索引 root/internal pages 使用通用 pin/hot policy。

正确性风险：

- 中。不能牺牲 page flush、dirty tracking、checkpoint 和 recovery。

## 13. 计划器继续完善索引覆盖、索引顺序和 INLJ 选择

预期收益：中等。

证据与背景：

- 现有 planner 已选择最长前缀匹配索引，但仍不是完整代价优化。
- 题目七和性能测试都强调 INLJ、范围查询和非主键字段查询。

建议方向：

- 支持覆盖索引扫描，查询列完全在索引键内时避免回表。
- 利用索引顺序满足 `ORDER BY` 或减少 sort。
- 对 join 右侧索引选择加入简单代价模型，避免在低选择性场景误用索引。

正确性风险：

- 中。需要保证输出顺序、重复行、NULL 之外的类型比较、聚合/order/limit 语义不变。

## 14. 输出与客户端响应路径继续瘦身

预期收益：小到中。

证据与背景：

- 已支持 `set output_file off`，性能测试明确依赖该开关减少 `output.txt` 写入。
- SELECT 大结果仍可能受 `BUFFER_LENGTH` 和格式化开销影响。

建议方向：

- 对非 SELECT 成功语句减少无意义 response 构造。
- 对 SELECT 格式化做批量 append，避免频繁 `fstream` 和小块 copy。
- 保持 `output.txt` 与客户端格式完全兼容。

正确性风险：

- 中。很多功能题严格比对输出格式，任何空格、换行、`Total record(s)` 变化都可能 WA。

## 15. 标准 perf FlameGraph、微基准和一致性压测体系

预期收益：间接收益，中长期很大，直接吞吐收益小。

证据与背景：

- 当前火焰图是 `gprof` flat profile 转 SVG，不是真正调用栈采样。
- 文档记录显示官方反馈周期长，本地需要更强的性能后一致性保护。

建议方向：

- 在可用环境中补一版 `perf record` + FlameGraph 的真实调用栈采样。
- 建立可重复的本地 TPCC-ish 微基准，分别覆盖 load、NewOrder、Payment、Delivery、StockLevel。
- 把 `q9_repro`、恢复检查、TPC-C invariant stress 串成提交前脚本。

正确性风险：

- 低。主要是工程工具建设，但能降低后续高风险优化的返工概率。

## 当前不建议推进的方向

- 不建议针对固定 TPC-C SQL 文本、表名、字段名写特判。
- 不建议为了提升吞吐关闭 WAL、跳过 commit flush、跳过 abort undo 或削弱恢复正确性。
- 不建议移除现有表记录内存化缓存、事务对象池、分片锁等优化来规避 bug；应在原设计内修复生命周期和一致性问题。
- 不建议优先 DML 批处理，除非已经有强回归覆盖 aborted partial writes、索引同步和 MVCC 可见性。

## 建议实施顺序

如果以“收益/风险比”而不是单纯收益排序，建议先做：

1. Release/O2/O3 构建验证。
2. 标准化本地微基准和一致性压测。
3. SQL parse/plan cache 原型。
4. `snapshot_rids()` 和只读批处理优化。
5. WAL group commit 小步验证。
6. 索引并发与稳定记录句柄等高风险优化。
