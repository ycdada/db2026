## 生成环境与方法

沿用原有 gprof-based 火焰图生成流程。当前环境仍以 `gprof` flat profile 转 SVG，不是真正的 `perf record` 调用栈 FlameGraph。

profiling 构建目录为 `build-profile/`，本次确认关键构建参数为：

```bash
CMAKE_BUILD_TYPE=Release
CMAKE_CXX_FLAGS="-Wall -O0 -g -ggdb3 -pg -fno-omit-frame-pointer"
CMAKE_EXE_LINKER_FLAGS="-pg"
```

重新构建并生成：

```bash
cmake --build build-profile -j
python3 profiling/generate_flamegraph.py --iterations 250
cp profiling/rmdb_flamegraph.svg todolists/火焰图2.svg
```

脚本启动 `build-profile/bin/rmdb`，创建临时 profiling 数据库，建 TPC-C 风格小表，加载 `src/test/performance_test/table_data/` 数据，然后循环执行 250 轮 OLTP-style SQL workload。


## 初步观察

- `BufferPoolManager::BufferPoolManager` 占比最高，说明本次 gprof 采样显著包含 server 启动阶段。当前全局 `buffer_pool_manager` 会一次性构造 `BUFFER_POOL_SIZE = 65536` 个 `Page`，每个 `Page` 构造时 `reset_memory()`，而 `data_[PAGE_SIZE] = {}` 也会清零，启动阶段容易触碰约 256MB 页面内存。
- parser/lexer/planner 仍在顶部：`yylex()`、`yyparse()`、`Planner::do_planner()` 各 5.56%。当前 exact SQL plan cache 已能缓存完全相同 SQL，但 workload 中常量不断变化，说明“SQL 模板规范化 + 参数绑定”的收益仍然很大。
- `yysyntax_error()` 出现在热点中，虽然不一定代表真实语法错误路径频繁失败，也提示 parser 生成代码在 `-O0 -pg` 下开销明显；这个信号应与 parser 缓存、lexer buffer 生命周期一起看。
- `IndexScanExecutor::load_visible_rid()`、`RmFileHandle::get_record_handle()`、`IndexScanExecutor::NextBatch()` 同时出现，说明第 6 项稳定句柄已经进入索引扫描热路径；但上层 `Next()`/`NextBatch()` 仍需复制输出 `RmRecord`，后续需要 borrowed record pipeline 才能继续放大收益。
- `RmFileHandle::snapshot_rids()` 仍然可见，顺序扫描或 MVCC extra record 收集相关路径仍有优化空间。
- `LRUReplacer::pin()` 和 buffer pool fetch/unpin 相关函数调用量高，说明命中路径中替换器维护和 page table 查找仍是可继续瘦身的方向。
- `InsertLogRecord::serialize()` 进入采样，结合写密集 TPC-C 短事务，WAL 序列化、log record buffer 管理和 group commit 后续阶段仍值得推进。

## 与上一版火焰图的差异

- 上一版顶部是 `Page::Page()`，本次顶部聚合为 `BufferPoolManager::BufferPoolManager()`，本质仍指向 buffer pool 初始化/页面清零成本。
- parser/lexer/AST 构造析构仍然存在，但 exact SQL plan cache 和后续索引热路径优化后，热点形态更集中到“变常量 SQL 仍需 parse/plan”。
- 第 6 项实现后，`RmFileHandle::get_record_handle()` 已出现在采样结果中，说明索引扫描开始走稳定句柄路径；同时也暴露出该路径剩余的 `shared_ptr`/输出复制成本。

## 注意事项

- 本次 profiling 构建显式使用 `-O0 -pg`，会放大 parser、STL、智能指针和虚调用开销；正式性能构建应以 Release/O3 结果为准。
- gprof flat profile 只有 self time，没有真实调用栈归因；`todolists/火焰图2.svg` 是便于观察的近似火焰图，不适合替代标准 perf FlameGraph。
- 因启动初始化占比很高，未来优化排序需要区分“启动/恢复性能”和“稳态 TPC-C 吞吐”。对 360 秒正式测量窗口来说，buffer pool 启动优化的 tpmC 直接收益可能小于其在本次火焰图中的占比。
