# 热力图输出

本文档记录 2026-07-04 基于当前项目代码重新生成的 RMDB profiling 热力图。数据来源是 `gprof` flat profile，因此这里的“热力图”是按 self time 与调用频次整理出的热点表，不是硬件事件级 perf heatmap。

- 生成脚本：`profiling/generate_flamegraph.py`

## 生成方式

本次先重新构建 profiling 版本，再运行 250 轮 TPC-C 风格短事务 workload：

```bash
cmake --build build-profile -j
python3 profiling/generate_flamegraph.py --iterations 250
```

脚本启动 `build-profile/bin/rmdb`，创建临时 profiling 数据库，建 TPC-C 风格小表，加载 `src/test/performance_test/table_data/` 数据，然后执行 250 轮 OLTP-style SQL workload。

注意：本 profile 构建使用 `-O0 -pg`，会放大 STL、智能指针、虚调用和 parser 生成代码开销；`gprof` flat profile 也缺少真实调用栈归因。下面的排序适合定位方向，不适合作为最终 Release/O3 吞吐占比。

## 结论

- 当前最热的单点是 `BufferPoolManager` 启动初始化，适合优先做懒初始化、去重清零和 frame 分配策略优化。
- 若只看稳态 TPC-C 短事务吞吐，最值得优先看的不是启动项，而是 `LRUReplacer::pin/unpin`、`LockManager::lock/unlock`、executor 临时对象生命周期、`select_from` 和模板绑定路径。
- SQL 模板计划缓存已经明显生效：parser/planner self time 退场，但 SQL 规范化、参数绑定、plan clone 和对象析构成为下一层成本。
- 后续优化应继续保持通用机制，避免对固定 TPC-C SQL、表名或字段名做特判。
