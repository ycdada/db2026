# 未来优化方向4

本文档基于 `todolists/热力图输出.md`、`profiling/rmdb_gprof.txt` 和当前代码状态整理，按预期性能收益从大到小排序。排序同时参考当前 `gprof` self time 与调用频次；其中第 1 项主要提升启动、恢复和短测量窗口，第 2 项以后更偏向稳态 TPC-C 吞吐。

排序原则：

- 优先处理当前热力图中 self time 明显或调用频次极高的通用路径。
- 已完成的 SQL 模板计划缓存不重复列为主方向，只保留下一阶段剩余成本。
- 不允许针对固定 TPC-C SQL、表名、字段名或常量写特判。
- 高风险优化必须配套功能回归、恢复测试和前后性能对比。

## 1. Buffer Pool 懒初始化、Page 清零去重与 frame 分配瘦身

预期收益：极大，主要提升启动、恢复、短 benchmark 窗口；稳态间接受益中等。

热力图证据：

- `BufferPoolManager::BufferPoolManager(unsigned long, DiskManager*)` 占 70.59% self time。
- 当前 profile 顶部热点只调用 1 次，说明成本集中在启动阶段一次性 buffer pool 初始化。

建议方向：

- 检查 `Page` 构造和 `reset_memory()` 是否存在重复清零，保证只在新页、frame reuse 或安全边界清理。
- 将 buffer frame 从启动期全量触碰改为懒分配或分批初始化。
- 保持 dirty page、free list、replacer、page table 语义不变，不能因为懒初始化泄露旧数据。
- 为启动、建库、恢复重启和短事务压测分别记录前后耗时，避免只看 gprof 样本。

正确性风险：中高。必须覆盖新页读取、淘汰重用、脏页刷盘、checkpoint、recovery 后 frame 复用和 destroy/recreate。

## 2. BufferPool 热页命中路径和 LRU pin/unpin fast path

预期收益：很大，主要提升稳态吞吐。

热力图证据：

- `LRUReplacer::pin(int)` 占 11.76% self time。
- `BufferPoolManager::fetch_page()` 5085 次、`unpin_page()` 5117 次、`page_table_.find(PageId)` 10266 次。

建议方向：

- 对 page table 命中的热页路径减少锁持有时间和重复 replacer 操作。
- 对 index root/internal page 或高频页设计通用热页保护策略，不能按表名固定常驻。
- 避免每次命中都做昂贵的 LRU list/hash 维护，可评估访问计数采样、二级 hot set 或延迟 unpin 合并。
- 拆分微基准：纯点查、索引点查、顺序扫描、插入更新混合，分别看 fetch/pin/unpin 次数变化。

正确性风险：高。必须保证 pin count、淘汰安全、脏页刷盘、并发 fetch/unpin、delete_page 和 recovery 后一致性。

## 3. Lock Manager 与短事务状态轻量化

预期收益：很大，主要提升稳态短事务吞吐。

热力图证据：

- `LockManager::unlock(Transaction*, LockDataId)` 占 5.88% self time，调用 20000 次。
- `LockManager::lock(...)` 11250 次，`lock_shared_on_record(...)` 9250 次，lock table erase/operator[] 调用也很高。
- `TransactionManager::HasMvccState()` 9750 次、`IsMvccTxn()` 4500 次。

建议方向：

- 为隐式短事务建立更轻的 lock/unlock 路径，减少 map 查找、请求队列构造和读写集小对象分配。
- 缓存事务隔离级别、MVCC 状态和只读/只写路径判断，避免每条语句重复判断。
- 对 LockDataId、LockRequest、事务读写集容器做小对象复用或内联小容量存储。
- 保留显式事务、SER/SI 冲突检测、死锁处理和 abort 清理语义。

正确性风险：很高。必须覆盖 2PL、显式事务、多记录锁、读写冲突、abort、commit 后释放锁和并发压测。

## 4. 简单 DML/点查的参数化 fast executor

预期收益：大。

热力图证据：

- `QlManager::select_from(...)` 占 5.88% self time。
- `Portal::start()` 3017 次，`IndexScanExecutor::beginTuple()` 1750 次，`advance_to_next_match()` 3500 次，`IndexScanExecutor::NextBatch()` 1000 次。
- `eval_conds()` 10000 次，说明点查、更新和扫描仍频繁做谓词重检。

建议方向：

- 在 planner 确认安全后，为单表索引点查、点更新、简单 insert/delete 提供通用 fast executor。
- 复用参数化计划，执行期只绑定参数、取 RID、做 visible record recheck，然后执行输出或写入。
- 合并不必要的 `Portal`、`ProjectionExecutor`、`IndexScanExecutor` 中间对象和小 vector 分配。
- 对 UPDATE/DELETE 保留谓词重检、写写冲突、MVCC 版本写、abort undo、索引维护和 WAL 顺序。

正确性风险：很高。必须覆盖 insert/update/delete/select、索引与非索引条件、MVCC 可见性、回滚、恢复和输出格式。

## 5. Condition/Value/TabCol/ColMeta 生命周期瘦身

预期收益：大。

热力图证据：

- `std::vector<Condition>::~vector()` 占 5.88% self time，调用 19846 次。
- `Value::~Value()` 11440 次、`ColMeta::~ColMeta()` 11344 次、`TabCol::TabCol(const&)` 11150 次。
- `bind_value()` 9659 次，`bind_conditions()` 4383 次，说明模板命中后参数绑定和 plan clone 成为主要剩余前端成本。

建议方向：

- 在 plan clone 和参数绑定路径中减少深拷贝，能原地覆盖参数的 Value 不重复构造 raw buffer。
- 对 `Condition`、`SetClause`、`TabCol`、`ColMeta` 常见小 vector 预留容量或使用小容量内联容器。
- 拆分只读元数据和执行期参数，把不可变结构放在缓存 plan 中共享，执行期只保存轻量参数视图。
- 保持 schema version、DDL/load 失效和错误报告语义。

正确性风险：高。生命周期稍有错误就可能造成 plan cache 污染、旧参数串用、定长字符串填充错误或析构后悬空。

## 6. Borrowed record pipeline 与 record/shared_ptr 成本下降

预期收益：中到大。

热力图证据：

- `RmFileHandle::get_record(...)` 8000 次。
- `RmRecord` shared_ptr destroy/dispose 各 11626 次，`std::_Sp_counted_base::_M_release()` 53726 次。
- `ProjectionExecutor::NextBatch()`、`IndexScanExecutor::NextBatch()`、`SeqScanExecutor::load_visible_current()` 调用频繁。

建议方向：

- 为 executor 增加 borrowed record 只读视图，SELECT 输出前最后一步再 materialize。
- 对索引点查和顺序扫描统一传递 `const RmRecord*` 或轻量 record view，减少 `unique_ptr/shared_ptr` 级联复制。
- MVCC undo version、extra record 和需要跨生命周期保存的记录仍保持 owned record。
- 评估稳定句柄中 shared_ptr 引用计数成本，必要时引入 generation 校验的轻量 handle。

正确性风险：很高。必须证明 update/delete/abort/close/reopen/destroy/recreate 后不会悬空，不会读到错误版本。

## 7. SQL 模板缓存第二阶段：降低规范化、绑定和 cache 对象成本

预期收益：中到大。

热力图证据：

- `append_normalized_token(...)` 417206 次，`next_token(...)` 13628 次。
- `SqlTemplate::~SqlTemplate()` 11596 次，`TemplateLiteral::~TemplateLiteral()` 750 次。
- `yyparse()/Analyze/Optimizer` 降到 526 次，`Planner::do_planner()` 降到 26 次，说明第一阶段已把主要收益吃到，剩余成本集中在模板前置处理和绑定。

建议方向：

- 缓存最近 SQL 文本到模板 key 的映射，避免同一连接内重复 tokenize。
- 对模板 literal、param spec、normalized buffer 做对象复用或短字符串优化。
- 扩大模板缓存覆盖面时保持通用语义，例如更多 SELECT 形态、ORDER/LIMIT、复杂谓词，但不写固定 SQL 特判。
- 增加 cache 命中率、失效率、模板数量和平均绑定耗时统计。

正确性风险：中高。必须保证 DDL/load/schema version 后失效准确，参数类型和错误信息不串用。

## 8. SeqScan 快照缓存与扫描游标瘦身

预期收益：中等。

热力图证据：

- `SeqScanExecutor::load_visible_current()`、`RmScan::next()`、`RmScan::rid()` 各 7500 次。
- `RmFileHandle::snapshot_rids()` 258 次，排序相关函数仍出现。

建议方向：

- 为表记录缓存维护 generation + Rid snapshot cache，只在 insert/delete/reset/recreate 后重建。
- 对只读短扫描提供 cursor 式遍历，减少每次扫描复制完整 Rid vector。
- 对 MVCC/SER 谓词读保留必要读集，不能因跳过 snapshot 漏掉范围读依赖。

正确性风险：中高。必须覆盖 delete tombstone、abort insert rollback、GC、文件 close/reopen 和表重建。

## 9. WAL 序列化与 log buffer 批量 append 后续阶段

预期收益：中等，写密集场景可到中到大。

热力图证据：

- `LogManager::add_log_to_buffer(...)` 1941 次。
- `InsertLogRecord::serialize(...)` 1182 次，`flush_log_to_disk()` 260 次，`TransactionManager::commit()` 276 次。

建议方向：

- 对常见 log record 使用线程本地 scratch buffer 或预分配 buffer，减少短事务反复分配和 copy。
- 将 log buffer append 改为更低锁竞争的批量结构，提交等待 durable LSN。
- 继续验证 group commit 在多连接写入下的收益，不削弱 WAL 持久化语义。

正确性风险：很高。不能破坏 WAL 先于数据页、commit durable、abort undo、crash recovery 和 checkpoint。

## 10. B+Tree 节点内查找与索引扫描状态缓存

预期收益：中等。

热力图证据：

- `IxNodeHandle::lower_bound(...)` 4049 次，`internal_lookup(...)` 2902 次。
- `IndexScanExecutor::advance_to_next_match()` 3500 次，`IndexScanExecutor::cols()` 6250 次。

建议方向：

- 对只读点查缩短 latch 范围，缓存 root/internal page 的通用访问路径。
- 对 executor 内重复 `cols()`、`find_col()`、索引元数据查找做构造期缓存。
- 写路径先保持安全，再评估 leaf-level latch coupling。

正确性风险：高。需要覆盖索引插入、删除、更新、分裂、恢复后 heap-index 对齐和并发读写。

## 11. 输出路径与 SELECT response 构造瘦身

预期收益：小到中。

热力图证据：

- `QlManager::select_from(...)` 有 5.88% self time。
- workload 已执行 `set output_file off`，但客户端 response 仍需构造。

建议方向：

- 对 SELECT 结果批量 append，减少小字符串拼接和临时对象。
- 对非 SELECT 成功语句统一轻量返回路径。
- 维持功能测试要求的空格、换行、截断和 `Total record(s)` 格式。

正确性风险：中。输出格式微小变化可能影响端到端测试。

## 12. 标准 perf FlameGraph 与分阶段 profiling

预期收益：间接收益大，直接吞吐收益小。

热力图证据：

- 当前 gprof self time 总量只有 0.17 秒，且 `-O0 -pg` 会放大 STL 和 parser 生成代码成本。
- 启动期 `BufferPoolManager` 占比很高，会影响对稳态吞吐热点的判断。

建议方向：

- 将 profiling 拆成启动、load、稳态事务、恢复重启四个阶段。
- 在可用环境中补充 `perf record` + FlameGraph，获取真实调用栈。
- 固化 benchmark 输出 median、p95、TPS/tpmC、cache 命中率和 correctness invariant。

正确性风险：低。属于工具建设，但能显著降低后续高风险优化的误判。

## 当前不建议推进的方向

- 不建议关闭 WAL、跳过 commit flush 或削弱 recovery 来换性能。
- 不建议为了命中 fast path 写固定 TPC-C SQL、表名或字段名特判。
- 不建议回退已完成的 SQL 模板计划缓存；应继续压缩其规范化和绑定成本。
- 不建议在没有并发和恢复回归前大改 B+Tree latch 协议。
