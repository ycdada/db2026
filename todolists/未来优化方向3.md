# 未来优化方向3

本文档基于 `todolists/火焰图2.md`、`todolists/新未来优化方向.md` 和当前代码状态整理，只列仍值得继续推进的后续方向，并按预期性能收益从大到小排序。收益主要面向 TPC-C 稳态吞吐；若某项主要提升启动、load 或恢复时间，会单独说明。

排序原则：

- 优先选择火焰图2中仍可见、且在 TPC-C 短事务中会高频重复的路径。
- 已完成的阶段不重复列为完成项，只列下一阶段可以继续放大收益的部分。
- 禁止针对固定 TPC-C SQL 文本、表名或字段名写特判；所有优化必须落在通用 parser、planner、executor、index、record、buffer、transaction 或 WAL 机制中。
- 高收益高风险项必须配套 correctness regression、恢复测试和小基准。

## 1. SQL 模板规范化、参数绑定与可复用执行计划

实施状态：已完成第一阶段。当前服务端在 exact SQL plan cache 之外新增了 DML 模板缓存：对 SQL 文本做词法级模板化，将数字和字符串字面量归一为 `?`；第一次 parse/analyze/plan 后，为 AST/语义 `Value` 标注 `param_id`，缓存带参数位置的 plan；后续同模板不同常量 SQL 命中时，深拷贝缓存 plan，并按新字面量重绑定 `Value` 与 raw buffer，从而跳过 parser/analyze/planner。DDL、load、事务控制和无法完整绑定参数的复杂语句仍走原路径。

预期收益：极大。

火焰图证据：

- `yylex()`、`yyparse()`、`Planner::do_planner()` 各占 5.56%。
- 大量 AST、`Condition`、`TabCol`、`ColMeta`、`Value` 构造析构和 vector 拷贝调用仍出现在 profile 中。

当前状态：

- exact SQL 级 plan cache 已完成第一阶段，但只命中完全相同 SQL。
- TPC-C workload 的 SQL 模板固定但常量变化，当前仍会反复 parse/analyze/plan。

建议方向：

- 对 DML SQL 做通用模板规范化：保留语法结构、表列引用和操作符，把字面量抽取为参数。
- 缓存 parse/analyze/plan 产物，并在执行前快速绑定参数值。
- plan cache key 必须包含 schema version、隔离级别相关开关、输出格式相关语义和 DDL/load/checkpoint 失效版本。
- 避免按固定表名或固定 SQL 文本手写分支，规范化逻辑应服务所有等价 SQL 模板。

正确性风险：

- 高。必须保证类型转换、字符串定长填充、谓词比较、索引选择、事务可见性和错误报告语义不变。
- 本轮验证：`cmake --build build -j` 通过；`./build/bin/unit_test --gtest_brief=1` 11 个测试通过；`ctest --test-dir build --output-on-failure` 通过；端到端验证同模板不同常量的 `select`、`update`、`insert`、`delete` 均按新常量返回正确结果。

## 2. 简单 DML/点查的参数化 fast executor

预期收益：很大。

火焰图证据：

- parser/planner 之外，`Portal::start()`、`Portal::convert_plan_executor()`、`IndexScanExecutor::beginTuple()`、`IndexScanExecutor::advance_to_next_match()`、`ProjectionExecutor::NextBatch()` 等执行器装配和虚调用路径仍大量出现。
- `IndexScanExecutor::load_visible_rid()`、`IxIndexHandle::get_value()`、`eval_conds()` 说明主键/复合索引点查仍是核心路径。

当前状态：

- 索引等值点查已能走单 RID `get_value()`，但仍经 portal/executor 链构造和虚调用。

建议方向：

- 在 planner 确认安全后，为单表索引点查、点更新、简单 insert/delete 提供通用 fast executor。
- 复用参数化计划，执行期只绑定参数、取 RID、做 visible record recheck、执行更新/插入和索引维护。
- 合并不必要的 `ProjectionExecutor`、`IndexScanExecutor` 中间对象和小 vector 分配。

正确性风险：

- 很高。UPDATE/DELETE 必须保留 predicate recheck、写写冲突、MVCC 版本写、abort undo、索引一致性和 WAL 顺序。

## 3. Borrowed record pipeline 与索引扫描零中间副本

预期收益：大。

火焰图证据：

- `RmFileHandle::get_record_handle()`、`IndexScanExecutor::load_visible_rid()`、`IndexScanExecutor::NextBatch()` 同时进入采样。
- 第 6 项句柄层已经减少一次索引命中后的中间副本，但 `Next()`/`NextBatch()` 对外仍复制 `RmRecord`。

当前状态：

- 记录缓存提供 `shared_ptr<const RmRecord>` 稳定句柄。
- MVCC extra record、输出接口和投影路径仍以 owned `RmRecord` 为主。

建议方向：

- 为 executor 增加 borrowed record 只读视图，允许 Projection/Filter/Join 在安全生命周期内读取 `const RmRecord*` 或轻量 view。
- SELECT 输出前最后一步再 materialize，避免每层 executor 都构造 `unique_ptr<RmRecord>`。
- 对 MVCC visible record 和 undo version 保持 owned record，避免借用已失效版本。
- 评估 `shared_ptr` 句柄的引用计数成本，必要时引入带 generation 校验的轻量 handle。

正确性风险：

- 很高。必须证明 update/delete/abort/close/reopen/destroy/recreate 后 borrowed record 不悬空、不读错版本。

## 4. WAL 序列化、log buffer 池化与 group commit 后续阶段

预期收益：大。

火焰图证据：

- `InsertLogRecord::serialize()` 进入采样。
- `LogManager::add_log_to_buffer()`、`WriteRecord`、事务提交相关调用量高。

当前状态：

- group commit 第一阶段已完成，提交/回滚等待自身 commit/abort LSN 持久化。
- log record 构造、序列化和 buffer copy 仍在前台事务路径。

建议方向：

- 对常见 log record 使用预分配 buffer 或线程本地 scratch buffer，减少短事务反复分配和序列化 copy。
- 将 log buffer 改为环形或批量 append 结构，降低锁持有时间和内存复制。
- 继续评估后台刷盘线程，提交路径等待 durable LSN，刷盘由后台批处理完成。

正确性风险：

- 很高。不能破坏 WAL 先于数据页、commit 持久化、abort undo、crash recovery 和 checkpoint 语义。

## 5. Buffer Pool 懒初始化与热页命中路径瘦身

预期收益：启动/恢复极大；稳态吞吐中到大。

火焰图证据：

- `BufferPoolManager::BufferPoolManager()` 占 58.33%，显著指向启动阶段 buffer pool 初始化。
- `LRUReplacer::pin()`、`BufferPoolManager::fetch_page()`、`BufferPoolManager::unpin_page()` 调用量高。

当前状态：

- `BUFFER_POOL_SIZE = 65536`，启动时一次性构造大量 `Page`。
- `Page` 构造调用 `reset_memory()`，成员 `data_[PAGE_SIZE] = {}` 也会清零，存在重复清零风险。

建议方向：

- 去除 `Page` 构造阶段重复清零，确保只在 new page、frame reuse 或安全边界处清理。
- 评估懒分配 page frame，避免 server 启动一次性触碰所有 buffer 内存。
- 对 page table 命中的热页读取路径减少 replacer pin/unpin 维护，或引入热页/索引 root/internal page 的通用保护策略。
- 不按固定表名常驻页面，应基于访问频率、page type 或 root/internal page 属性设计通用策略。

正确性风险：

- 中高。新页、淘汰页、脏页刷盘、checkpoint、recovery 后重用 frame 都不能泄露旧数据或丢 dirty 标记。

## 6. `snapshot_rids()` 与顺序扫描快照缓存

预期收益：中到大。

火焰图证据：

- `RmFileHandle::snapshot_rids() const` 仍占 2.78%。
- `SeqScanExecutor::load_visible_current()`、`RmScan::next()`、`RmScan::rid()` 调用量仍高。

当前状态：

- `RmScan` 构造时会复制并排序当前 Rid 集合。
- MVCC extra record 收集和顺序扫描路径仍可能重复构造扫描快照。

建议方向：

- 为表记录缓存维护 generation + Rid snapshot cache，只有 insert/delete/reset/recreate 后才重建。
- 对只读短扫描提供 cursor 式遍历，减少每次扫描复制完整 Rid vector。
- 对 MVCC/SER 谓词读保留必要读集，不能因跳过 snapshot 漏掉范围读依赖。

正确性风险：

- 中高。必须覆盖 delete tombstone、abort insert rollback、GC、文件 close/reopen 和 recreate lifecycle。

## 7. 索引并发与 B+Tree hot path 继续优化

预期收益：中到大；并发场景可达大。

火焰图证据：

- `IxIndexHandle::get_value()`、`IxNodeHandle::lower_bound()`、`IxNodeHandle::internal_lookup()` 调用量高。
- TPC-C 主路径高度依赖复合索引点查和插入。

当前状态：

- 唯一索引点查已避免临时 vector。
- 写路径仍主要依赖较粗粒度保护，尚未做完整 latch coupling 或乐观读。

建议方向：

- 对只读点查引入乐观读或更短 latch 范围。
- 对 root/internal hot page 加通用缓存或更轻量访问路径。
- 写路径先保持安全，逐步引入 leaf-level latch coupling，覆盖分裂、合并、回滚和 recovery 后一致性。

正确性风险：

- 高。需要索引一致性、并发插入/删除/更新、crash recovery 后 heap-index 对齐测试。

## 8. Lock Manager 与事务状态轻量化

预期收益：中到大。

火焰图证据：

- `LockManager::lock()`、`LockManager::unlock()`、`lock_shared_on_record()`、`lock_exclusive_on_record()` 调用量高。
- `EnsureStatementTransaction()`、`TransactionManager::IsMvccTxn()`、`HasMvccState()` 高频出现。

当前状态：

- Lock Manager 已做分片，事务对象池已有保守复用。
- 每条短语句仍频繁进入锁、事务和隔离级别判断路径。

建议方向：

- 对隐式短事务建立更轻的 statement transaction fast path。
- 缓存事务隔离属性和 MVCC 状态判断，减少重复虚/函数调用。
- 对 LockRequest、读写集小对象做线程本地池化，配套 reset/poison 检查。

正确性风险：

- 高。不能破坏 2PL、SI/SER 读写冲突、死锁处理、显式事务状态和 abort 清理。

## 9. Parser/AST 内存 arena 与 vector reserve 微优化

预期收益：中等。

火焰图证据：

- AST 节点、`shared_ptr`、`std::vector<Condition>`、`std::vector<TabCol>`、`Value` 等构造析构调用非常多。
- `yysyntax_error()`、lexer buffer 切换函数也高频出现。

建议方向：

- 若参数化模板缓存无法覆盖的 SQL 仍很多，可为 parser/analyze 阶段引入请求级 arena 或对象池。
- 在 analyze/planner 中根据 AST 大小预估 reserve 常见 vector，减少 `_M_realloc_insert`。
- 减少不必要的 `shared_ptr` 层级复制，能用值类型或 `unique_ptr` 的内部临时结构不要额外共享所有权。

正确性风险：

- 中。主要是生命周期和错误路径释放，必须避免 AST 被 plan cache 持有后 arena 提前释放。

## 10. 输出路径与 SELECT 格式化继续瘦身

预期收益：小到中。

火焰图证据：

- `QlManager::select_from()`、`RecordPrinter::print_record_count()`、Projection/Select 输出路径仍出现。
- workload 已执行 `set output_file off`，但客户端 response 仍需要构造。

建议方向：

- 对 SELECT 结果批量 append，减少小块字符串拼接和临时对象。
- 对非 SELECT 成功语句返回路径继续瘦身。
- 保持功能测试输出格式完全兼容。

正确性风险：

- 中。输出空格、截断、换行和 `Total record(s)` 格式都可能影响功能测试。

## 11. 标准 perf FlameGraph 与分阶段 profiling

预期收益：间接收益大，直接吞吐收益小。

火焰图证据：

- 当前 gprof flat profile 被启动阶段明显影响，且没有调用栈归因。
- `-O0 -pg` 会放大 STL/parser/智能指针成本，不等于 Release/O3 稳态 profile。

建议方向：

- 在可用环境中生成 `perf record` + FlameGraph 的标准调用栈版本。
- 将 profiling 拆成启动、load、稳态 NewOrder/Payment/Delivery/StockLevel、恢复重启几个阶段。
- 建立固定脚本输出 median/p95 和 correctness invariant，避免只看单次 gprof 样本。

正确性风险：

- 低。属于工具建设，但能显著降低后续高风险优化的误判概率。

## 当前不建议推进的方向

- 不建议为了降低日志热点关闭 WAL、跳过 commit flush 或削弱 recovery。
- 不建议把 fast path 写成固定 TPC-C SQL、表名或字段名匹配。
- 不建议为了消除 `get_record_handle()` 热点回退稳定句柄优化；应继续沿 borrowed record pipeline 扩展。
- 不建议在没有并发和恢复回归前大改 B+Tree latch 协议。
