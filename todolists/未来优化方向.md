# 未来优化方向

本文档用于记录本项目在 TPC-C 性能测试方向上已经采用的优化、参考项目中出现但本项目未确认采用的优化，以及后续可继续推进的优化优先级。

事实来源以当前主项目代码为准；未跟踪目录 `T202510616995471-363/` 仅作为参考材料，不计入“本项目已采用”。

## 已采用的优化

### 1. 面向 TPC-C 访问路径的复合索引

性能测试 load 脚本中已经为核心表建立了贴合事务访问路径的索引：

- `warehouse(w_id)`
- `district(d_w_id, d_id)`
- `customer(c_w_id, c_d_id, c_id)`
- `new_orders(no_w_id, no_d_id, no_o_id)`
- `orders(o_w_id, o_d_id, o_id)`
- `order_line(ol_w_id, ol_d_id, ol_o_id, ol_number)`
- `item(i_id)`
- `stock(s_w_id, s_i_id)`

这些索引覆盖了 NewOrder、Payment、OrderStatus、Delivery 等事务中的高频点查和范围查路径，是当前吞吐提升的基础。

### 2. 规划器选择最长前缀匹配索引

`Planner::get_index_cols` 会根据条件列选择匹配前缀最长的索引，并应用到 `SELECT`、`UPDATE`、`DELETE` 的扫描计划中。该策略虽然不是完整代价优化器，但能稳定避免大量全表扫描。

### 3. 谓词转换为索引上下界

`IndexScanExecutor` 会将 `= / > / >= / < / <=` 条件转换为索引 lower/upper bound，并用 `lower_bound`、`upper_bound` 限定扫描区间。这样可以把大量 TPC-C 主键/复合键查询压缩到很小的扫描范围。

### 4. 聚簇化记录布局

当前实现将表的第一个索引作为聚簇顺序依据：

- `load_table` 在表已有索引时，按第一个索引顺序排序后插入记录。
- `create_index` 在为无索引表创建第一个索引时，会按该索引重排表记录并重建索引。

这让主访问路径上的相邻键更容易落在相近数据页中，有利于减少随机 I/O 和提升缓存命中。

### 5. Buffer Pool 分片

`BufferPoolManager` 已按 `PageIdHash` 将页面映射到多个 shard，每个 shard 拥有独立的 `page_table_`、`free_list_`、`LRUReplacer` 和 latch。相比全局单锁，分片可以降低并发 `fetch/unpin/flush` 的锁竞争。

### 6. 输出路径开关

系统支持 `set output_file off`，并在 `select`、`show tables`、`show index`、命令处理等路径检查输出开关，避免性能测试阶段把无关结果持续写入 `output.txt`。

### 7. 内存执行算子能力

当前执行层已经支持内存排序、聚合、Nested Loop Join、Index Nested Loop Join、Sort Merge Join 等能力。TPC-C 主事务通常以短事务点查/范围查为主，但这些能力对混合查询、统计查询和 explain 场景仍有价值。

### 8. 延迟复用的事务对象池

`TransactionManager` 已维护一个保守的事务对象池：事务结束后不会立刻复用，而是先进入按工作线程隔离的延迟队列；只有当前线程的队列超过安全窗口后才复用最老对象，避免其他线程在提交/回滚返回路径或上下文析构阶段仍持有旧指针时把对象重置成新事务。

当前只池化简单隐式只读事务，并要求事务生命周期内没有产生写记录，且锁集、索引页集合都已经清空；事务不属于 MVCC 或版本化写路径。显式事务、SI/SER 事务、有 MVCC 写键、发生过表/索引写入或存在残留状态的事务保留原行为，不进入对象池。

## 未采用或未确认的优化

### 1. 表记录全量内存化

参考项目中提到的“表记录保存在 `std::vector<char *>`、索引保存记录指针”的主路径，在当前主项目中未确认存在。当前项目仍以记录文件、页式存储、索引文件和 Buffer Pool 为核心路径。

如果未来要尝试热表常驻内存，需要设计为通用机制，不能针对固定 TPC-C 表名或 SQL 文本硬编码。

### 2. 执行器批处理

当前代码中存在 `NextBatch` 批处理接口残留，但为了修复 Phase 3 一致性问题，查询入口已恢复为单行火山模型消费。后续如果重新启用批处理，必须从只读 `SELECT` 路径开始，并避免先修改 `UPDATE/DELETE` 的 rid 收集逻辑。

## 未来优化优先级

1. 继续完善通用访问路径优化：复合索引覆盖、索引顺序利用、范围扫描、INLJ。
2. 重新设计执行器批处理时，只从只读 `SELECT` 路径开始；先建立本地一致性保护，再考虑 DML。
3. 评估锁请求池、日志缓冲池化，继续减少短事务频繁分配。
4. 评估热表/热索引常驻或更激进的 buffer-resident fast path，但必须保持通用性，避免 TPC-C 专用硬编码。
5. 优化 WAL 刷盘批处理和异步化，前提是保留 WAL 顺序、提交持久性和崩溃恢复正确性。
6. 建立本地微基准和性能后一致性检查，减少依赖 30 分钟一次的人工提交反馈。

## 后续工作规则

- 评分只能由用户手动提交，Codex 不自动提交评测。
- 提交后由用户反馈正确性结果、报错信息或得分，再据此继续修复或优化。
- 禁止通过反复提交枚举错误；高风险优化必须先有本地证据、代码路径分析或可复现检查。
- 文档和代码中不得把未经当前主项目代码确认的参考项目实现写成本项目已采用优化。
