## 2026-07-04 降低热点写冲突 abort

问题：项目当前 abort 率高。锁管理器原先采用 no-wait 2PL，不兼容锁会立即抛 `DEADLOCK_PREVENTION`。此外 UPDATE/DELETE 先用普通 scan 收集 RID，scan 阶段拿共享锁，随后执行器再升级到排他锁；多个事务更新同一热点行时容易形成 S->X 升级死锁，最终超时或 abort。

优化项：

- 将通用锁管理从立即 abort 改为条件变量等待，等待上限为 2s，超时后再按 deadlock prevention abort。
- UPDATE/DELETE 的候选 RID 收集阶段关闭共享读锁，实际修改阶段仍获取排他锁并重新检查条件，避免 S->X 升级死锁。
- SELECT 等普通读取路径保持原来的共享锁语义。

本地验证：

```bash
cmake --build build -j
./build/bin/unit_test
ctest --test-dir build --output-on-failure
```

结果：

- `unit_test`：12/12 passed。
- `ctest`：1/1 passed。
- 热点写冲突验证 1：4 个客户端并发，每个客户端执行 20 次 `begin; update hot set v=v+1 where id=1; commit;`，共 80 次热点行更新。
- 热点写冲突验证 2：8 个客户端并发，每个客户端执行 50 次同样的热点行更新，共 400 次更新。
- 验证结果：两轮均 `abort=0`，`failure=0`；第二轮最终 `select v from hot where id=1;` 返回 `400`。

备注：

- 该优化是通用并发控制机制，不依赖表名、字段名或固定 SQL。
- `scripts/profile_tpcc_sample.sh` 的小数据循环样本仍会产生部分 abort 噪声，需要继续拆分原因；本项提交主要解决热点写冲突下的锁等待和锁升级 abort。

## 2026-07-04 顺序扫描 RID 快照缓存

问题：火焰图中 `AggregateExecutor -> SeqScanExecutor -> RmScan::RmScan -> RmFileHandle::snapshot_rids` 是首轮明显热点。原实现每次构造 `RmScan` 都会从 `records` 哈希表遍历所有 RID、重新排序并复制到扫描器本地 vector。聚合、范围查询和 DML 候选扫描会频繁触发该成本。

优化项：

- 在 `RmFileHandle::SharedRecordState` 中缓存不可变的有序 RID 快照。
- `RmScan` 持有 `shared_ptr<const vector<Rid>>`，避免每次扫描复制 RID 列表。
- 插入、删除、reset 数据页时失效快照；更新记录内容不改变 RID，不失效快照。
- 已开始的扫描持有旧快照，后续写入只会让新扫描重建快照，保证扫描期间列表稳定。

本地验证：

```bash
cmake --build build -j
./build/bin/unit_test
ctest --test-dir build --output-on-failure
g++ -std=c++17 -O3 -DNDEBUG -I. -Isrc build/rm_scan_bench.cpp \
  build/lib/librecord.a build/lib/libstorage.a build/lib/liblru_replacer.a \
  -lpthread -o build/rm_scan_bench
./build/rm_scan_bench
```

结果：

- `unit_test`：12/12 passed。
- `ctest`：1/1 passed。
- 微基准：50,000 条记录，第一次扫描构建快照 `first_us=2474`；随后 500 次缓存命中扫描 `repeated_us=49771`，平均 `avg_us=99`。

备注：

- 该优化是通用存储/执行机制，不依赖表名、字段名或固定 SQL。
- `build/rm_scan_bench.cpp` 位于被忽略的 `build/` 目录，仅作本地验证产物，不提交。

## 2026-07-04 事务控制语句计划缓存

问题：火焰图中 `yyparse`、`yylex`、`ast::SemValue` 仍有可见占比。已有 DML 精确 SQL 缓存和模板计划缓存，但 `begin;`、`commit;`、`abort;`、`rollback;` 这类高频事务控制语句不属于 DML，原先每次都会重新解析和规划。TPCC 每个事务都会执行事务控制语句，该开销会稳定放大。

优化项：

- 将不可变的事务控制 `OtherPlan` 纳入精确 SQL 计划缓存。
- 仅缓存 `begin/commit/abort/rollback`，不缓存 show/desc/checkpoint 等可能涉及元数据或输出副作用的 utility 语句。
- 缓存仍受全局 plan cache version 管理，DDL/load/checkpoint 等失效逻辑保持不变。

本地验证：

```bash

./build/bin/unit_test
ctest --test-dir build --output-on-failure
```

结果：

- `unit_test`：12/12 passed。
- `ctest`：1/1 passed。
- socket 微基准：同一连接重复执行 2000 轮 `begin; commit;`，共 4000 条事务控制语句，`bad=0`，耗时 `0.3286s`。

备注：

- 该优化是通用解析/计划缓存机制，不依赖表名、字段名或固定 SQL。

## 2026-07-04 宽表记录页上限与 READ COMMITTED 短读锁

问题：

- TPCC 样本中 `customer` 表记录长度为 752 字节，原记录管理层固定 `RM_MAX_RECORD_SIZE=512`，导致建表失败，后续访问该表的事务被回滚，表现为大量 abort 和锁残留等待。
- 多客户端样本中，默认 READ COMMITTED 事务先 `SELECT` 再 `UPDATE` 同一热点行时，长持有 S 锁会放大 S->X 升级等待，4 客户端短样本曾出现 12 条 abort。

优化项：

- 将记录大小上限改为按页可用空间计算：`PAGE_SIZE - Page::OFFSET_PAGE_HDR - sizeof(RmPageHdr) - 1`，并用相同页内 payload 公式计算每页可容纳记录数。
- `LockManager::unlock` 增加可选参数，允许释放短读锁时不进入 2PL shrinking；提交/回滚路径仍保持原语义。
- `SeqScanExecutor` 和 `IndexScanExecutor` 在 READ COMMITTED 下使用短读锁：读取记录时拿 S 锁，读完立即释放；如果事务已持有该 RID 的写锁则不释放，避免误放掉自身 X 锁。
- SI/SER 事务仍走现有 MVCC 读路径，不引入表名、字段名或固定 SQL 特判。

结果：

## 2026-07-04 无分组聚合执行器与扫描 fd 缓存

问题：

- 上一轮火焰图显示热点仍集中在 `AggregateExecutor -> SeqScanExecutor -> RmFileHandle::snapshot_rids/get_record`。
- 原 `AggregateExecutor` 对无 `GROUP BY` 的聚合也会为每行构造 group key、访问 `std::map`，并复制首行记录；`COUNT/SUM/MIN/MAX/AVG` 这类单组聚合在 TPCC 样本中会反复触发该开销。
- 扫描执行器每行加/解短读锁时都会调用 `RmFileHandle::GetFd()`，该函数内部会获取文件句柄共享锁，火焰图中可见。
- 高吞吐 8 客户端样本中偶发写锁等待超时，原因是后来的短读锁可越过前方等待的 X 锁，造成写者饥饿。

优化项：

- `AggregateExecutor` 对无分组聚合走单 `GroupState` 流式累计，跳过 group key 构造和 `std::map` 查询。
- 预绑定聚合参数列和分组列元数据，避免每行按表名/列名查找 `ColMeta`。
- 聚合执行器使用 `NextBatch` 拉取子执行器结果，减少逐行虚函数调用和控制流开销。
- `SeqScanExecutor`、`IndexScanExecutor` 在构造时缓存表 fd，扫描过程中不再逐行调用 `RmFileHandle::GetFd()`。
- 锁队列授予增加 FIFO 约束：后来的请求不能越过队列中更早的不兼容等待者；锁等待上限从 2s 调整为 10s，降低热点长事务被误判为 deadlock 的 abort。

本地验证：

```bash

./build/bin/unit_test
ctest --test-dir build --output-on-failure
cmake --build build-profile -j
scripts/profile_tpcc_sample.sh --duration 8 --clients 8 -o build/profile-tpcc-8c-aggfd-fifo10
```

额外语义验证：

- socket 临时库执行 `count(*)` 空结果、`count(*)` 非空、`sum(v)`、`min(v)`、`max(v)`、`avg(v)`，结果分别为 `0/3/60/10/30/20.000000`。

结果：

- `unit_test`：12/12 passed。
- `ctest`：1/1 passed。
- 8 客户端 TPCC 样本：`build/profile-tpcc-8c-aggfd-fifo10/workload.log` 为 0 字节，`SQL failed` 数为 0，生成 `build/profile-tpcc-8c-aggfd-fifo10/flamegraph.svg`。
- 粗略火焰图对比：`AggregateExecutor::beginTuple` 累计样本从上一轮 `3846421083` 降至 `2865586004`；`RmFileHandle::GetFd` 累计样本从 `282719136` 降至 `9719746`。

备注：

- 本轮优化均为通用执行器、扫描器和锁队列机制，不依赖 TPCC 表名、字段名或固定 SQL。
- 当前后续热点主要集中在顺序扫描取记录、记录复制、解析/计划构造、SELECT 数值格式化和部分索引扫描执行器构造。

## 2026-07-04 高并发 abort 收敛：延长热点锁等待与回滚幂等恢复

问题：

- 官方反馈当前 abort 率偏高。已有锁队列从 no-wait 改为等待式 2PL，但热点写锁等待上限只有 10 秒；在服务器抖动或更高并发下，正常排队可能被误判为 `DEADLOCK_PREVENTION` abort。
- 本地排查中，较激进的死锁检测会让事务更早 abort，并暴露出非 MVCC 删除回滚路径不幂等：固定 RID 恢复时如果记录已存在，会抛出 `Record already exists`，导致服务端线程异常终止。

优化项：

- 将通用锁等待上限从 10 秒提高到 60 秒，降低热点行正常排队被超时误杀的概率。
- 保留锁队列 FIFO 约束，后来的不兼容请求不能越过更早等待者；锁升级请求也进入同一 FIFO 队列，避免 S->X 升级被后续读锁持续插队。
- 非 MVCC `DELETE_TUPLE` 回滚改为幂等恢复：目标 RID 已存在时先删除当前索引项并 update 成旧记录，不存在时才固定 RID insert，然后插回旧索引项。

本地验证：

```bash

scripts/profile_tpcc_sample.sh --duration 16 --clients 32 -o build/profile-tpcc-32c-timeout60

git check-ignore -v build/profile-tpcc-32c-timeout60/flamegraph.svg build/profile-tpcc-32c-timeout60/perf.data build/profile-tpcc-32c-timeout60/stacks.folded
```

结果：

- `unit_test`：12/12 passed。
- `ctest`：1/1 passed。
- 32 客户端 TPCC 样本：`build/profile-tpcc-32c-timeout60/workload.log` 为 0 字节，`SQL failed` 数为 0，生成 `build/profile-tpcc-32c-timeout60/flamegraph.svg`。
- profile 产物确认被 `.gitignore` 的 `build/` 规则忽略，不会被 git 跟踪。

备注：

- 本轮优化是通用锁管理和事务回滚机制，不依赖表名、字段名、固定 SQL 或 TPCC 事务类型。
- 当前火焰图热点仍集中在聚合顺序扫描的 `RmFileHandle::get_record/snapshot_rids`、记录复制、锁等待和计划/执行器构造，下一轮继续按火焰图排除法处理。

## 2026-07-04 显式事务读改写 abort 收敛：Update 锁与升级优先

问题：

- 官方反馈 abort 率仍偏高。进一步用更贴近 `new_order` 的读-改-写模式复现：多个客户端在显式事务中先 `select` 同一计数行，再按读到的值 `update` 计数并插入唯一索引。原 READ COMMITTED 短读锁会让多个事务读到同一旧值，后续插入唯一索引出现大量 duplicate/failure。
- 如果简单让显式事务持有普通 S 锁，又容易在 S->X 升级时形成等待环；如果对所有显式事务读都持有 U 锁，则 join 读会和跨表写事务形成不必要的等待。

优化项：

- 在通用锁管理器中加入记录级 Update(U) 锁：U 与普通 S/IS 兼容，但 U 与 U/X 不兼容，用于显式 READ COMMITTED 事务中可能参与读-改-写的单表读。
- 已持锁事务升级到更强锁时，只等待其他已授予的不兼容锁，不被排在自己后面的等待者卡住，避免 U->X 升级自阻塞。
- `SeqScanExecutor`、`IndexScanExecutor` 支持由计划转换阶段控制是否使用 U 锁；普通 S 锁在 READ COMMITTED 下仍读完即释放。
- `Portal::convert_plan_executor` 对 join 子树禁用 U 锁，join 读保持短 S 锁，避免跨表 join 读与写事务形成等待环。

```bash
  build/profile-tpcc-32c-u-lock-short-s/perf.data \

```

结果：

- 读-改-写复现：8 个客户端，每个客户端 20 轮 `begin; select n; update n; insert unique; commit;`，共 160 轮，`bad=0`、`abort=0`、`dup=0`；最终计数为 161，插入订单数为 160。
- `unit_test`：12/12 passed。

- 4 客户端 TPCC 样本：`build/profile-tpcc-4c-u-lock-short-s/workload.log` 为 0 字节，生成 `flamegraph.svg`。

## 2026-07-04 记录缓存直接槽位定位

问题：

- 最新 32 并发火焰图中，聚合顺序扫描路径 `AggregateExecutor -> SeqScanExecutor -> RmFileHandle::get_record_handle_fast` 是最大热点之一。
- 原内存记录缓存主要通过 `unordered_map<int64_t, shared_ptr<RmRecord>>` 按 RID 查找。全表扫描已经有有序 RID 快照，但每行仍需要重新计算 key、哈希查找并取记录句柄。

优化项：

- 在 `RmFileHandle::SharedRecordState` 中增加按 `(page_no, slot_no)` 直接定位的 `record_slots` 槽数组。
- `get_record`、`get_record_handle_fast`、`is_record` 改为通过槽数组直接读取记录指针，保留原 `records` 哈希表用于兼容现有路径。
- 插入、固定 RID 插入、更新、删除、reset、打开文件加载记录时同步维护槽数组。
- 加载文件时只按真实已加载页数初始化槽数组，避免测试中人为写大 `num_pages` 时按 header 过度分配。

## 2026-07-04 READ COMMITTED 短读锁减少事务 lock_set 开销
