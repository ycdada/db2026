## 已确认 Bug 与修复

### 题目 8/9 输出格式冲突

- 时间：2026-06-23 14:18:08 +0800
- 场景：用 `pypdf` 抽取 `测试说明文档2026.pdf`，对照本地 Q8 smoke 与 Q9 harness。
- 结果：Q8 `commit/abort/index` 期待 `| id | name | score |` 旧简表；Q9 示例期待完整 `RecordPrinter`。Q9 示例一最终 T3 未执行 `SET`，但标准输出仍是完整格式。
- 结论：不能按“当前连接是否执行过 SET”切换格式；必须按“当前数据库/测试点是否出现过 isolation SET”切换。
- 验证：本地四类 Q8 smoke 均输出旧简表且最终态正确；Q9 harness 全部 `MATCH`，包括未 SET 的 T3 查询仍写完整格式；构建、unit_test、ctest、diff check 均通过。

### no-SET 写者破坏 SI 快照

- 时间：2026-06-22 21:10 后
- 场景：PDF 示例二中 T1 设置 SI，T2 只执行 `BEGIN; UPDATE; COMMIT;`，期望 T1 第二次 SELECT 仍为旧值 `100`。
- 结果：修复前按 PDF 原样复现会读到 T2 新值 `200`；`noset_dirty_read`、`noset_insert_vis`、`noset_delete_vis`、`noset_ww_conflict` 也均破坏 SI。
- 根因：非 MVCC/RC 写者走 executor `else` 分支原地改物理记录，不保留旧版本；SI 读者找不到 `MvccEntry` 时直接返回物理记录。
- 修复：新增 `TransactionManager::ShouldVersionWrites(txn)`，当写者自身是 SI/SER 或系统存在活跃 SI/SER 事务时，insert/update/delete 都进入版本保留路径；`GetVisibleRecord`、写冲突、SSI 检查和 planner 强制 SeqScan 仍按 `IsMvccTxn` 判定。
- 验证：`repro.py all` 全部 21 case `MATCH`，含 PDF 示例二、四个 no-SET blast-radius、范围写、读己写、SER 危险结构；`race 200` 0 bad；unit_test/ctest 通过。

### 全局隔离级别继承 hack 是误修

- 时间：2026-06-22 20:40 后
- 场景：曾尝试用进程级 `configured_isolation_level` / `MaybeInheritConcurrentMvccIsolation` 让未 SET 会话继承 SI。
- 结果：能修部分 no-SET 复现，但会把一个会话的 `SET SERIALIZABLE/SI` 泄漏给其它未 SET 会话；某变体导致线上分数下降并新增 `si/TupleReconstructTest` 失败。
- 结论：该方向已删除。后续不要恢复跨会话隔离级别继承；no-SET 写者问题应由写路径版本保留解决。
- 验证：删除后构建通过，unit_test 5/5、ctest 1/1；隔离级别仍按会话栈变量和事务对象传播。

### 多索引逻辑冲突 key 误判

- 时间：2026-06-22
- 场景：表 `two_idx(a,b)` 同时建 `index(a)` 与 `index(b)`；T1 旧快照插入 `(2,3)`，T2 在 T1 开始后提交 `(1,2)`。
- 结果：修复前 T1 插入 `(2,3)` 错误 abort，因为 `T1.a=2` 与 `T2.b=2` 的裸字节相同。
- 结论：MVCC 逻辑 key 必须带索引/列标识，不能只比较裸字节。
- 验证：修复后多索引场景不再误 abort，最终两行都存在。

### 无索引 UPDATE fallback 误判

- 时间：2026-06-22 19:17 后
- 场景：无索引表允许两行第一列相同，如 `(1,10),(1,20)`；两个 SI 事务分别更新不同 RID。
- 结果：修复前 `CheckMvccUniqueConflict(... self_rid != nullptr)` 仍用第一列 fallback 扫全表，会把不同 RID 的 UPDATE 误判为同一逻辑行冲突。
- 结论：无索引 fallback 只适用于 INSERT / DELETE-INSERT 的逻辑 key 特例；UPDATE 同 RID 冲突已有 `CheckMvccWriteConflict()`。
- 验证：fallback 收窄后，不同 RID UPDATE 均成功；无索引 DELETE/INSERT 同第一列仍 abort。

### 显式事务 abort 后“会话死状态”是误修

- 时间：2026-06-22 19:40 后
- 场景：曾让显式事务冲突 abort 后，同连接普通 SQL 被静默跳过，直到事务控制语句清理状态。
- 结果：该补丁会制造空输出，题面没有要求这种“会话死状态”，并很可能导致新增 `si/TupleReconstructTest` 失败。
- 结论：该逻辑已回退。后续不要把冲突 abort 后的连接强制变成静默死状态，除非拿到明确标准输出证据。

## 已排除或低优先级项

- 基础 SI 场景已通过：快照稳定读、first-committer-wins、读己写、索引键 UPDATE 可见性、DELETE 可见性、DELETE+INSERT、范围 UPDATE/DELETE、多版本链重构、SER 危险结构 abort。
- `si/Deadlock` 最小交错写：两行表中 T1 写 id=1、T2 写 id=2、T1 再写 id=2 时 T1 abort，T2 成功，最终 `(1,21),(2,22)`；本地符合预期。
- `si/Non_Repeatable_Read_Lost_Update` 最小调度：T1 旧快照重读保持旧值，后续 UPDATE abort，最终保留 T2 提交值；本地符合预期。
- 重复键 UPDATE：显式 SI 事务中 `UPDATE t SET id=2 WHERE id=1` 触发 `Duplicate key` 时，不污染 MVCC/物理状态。
- 同事务链式 UPDATE 条件重匹配：先 `UPDATE id=1 -> id=2` 后，`WHERE id=2` 可匹配新值，`WHERE id=1` 不再匹配。
- 多行范围写、DELETE 后重插旧快照读取、连续提交更新后的旧快照重构均已由 harness 覆盖并匹配。
- 并发 INSERT 同逻辑 key 竞态：50 轮/后续 200 轮未观察到 both-commit/both-abort；若隐藏用例仍有随机并发 insert mismatch，再考虑合并检查与登记临界区。
