# 火焰图输出

本文档记录本项目当前已生成的 RMDB 火焰图结果、生成方式和初步热点观察。

## 输出文件

- SVG 火焰图：`profiling/rmdb_flamegraph.svg`
- gprof 文本报告：`profiling/rmdb_gprof.txt`
- folded 数据：`profiling/rmdb_flamegraph.folded`
- 原始 gmon 数据：`profiling/rmdb_gmon.out`
- 生成脚本：`profiling/generate_flamegraph.py`

## 生成环境与方法

当前环境未发现 `perf` 或 FlameGraph 官方脚本，因此本次火焰图基于 `gprof` flat samples 生成。PDF 读取使用 Python `pypdf` 完成。

使用了独立 profiling 构建目录 `build-profile/`，构建参数包含：

```bash
cmake -S . -B build-profile \
  -DCMAKE_CXX_FLAGS="-Wall -O0 -g -ggdb3 -pg -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-pg"
cmake --build build-profile -j
```

生成命令。本仓库移动过路径，旧 `build-profile/` 的 CMake cache 不可复用；脚本已支持显式指定构建目录：

```bash
cmake -S . -B build-flame-local \
  -DCMAKE_CXX_FLAGS="-Wall -O0 -g -ggdb3 -pg -fno-omit-frame-pointer" \
  -DCMAKE_EXE_LINKER_FLAGS="-pg"
cmake --build build-flame-local -j
python3 profiling/generate_flamegraph.py --build-dir build-flame-local --iterations 5000
```

脚本会启动指定构建目录下的 `bin/rmdb`，创建临时 profiling 数据库，建 TPCC 小表，加载 `src/test/performance_test/table_data/` 中的小规模 CSV，然后循环执行 NewOrder 风格 SQL workload，最后输出 SVG、folded、gprof 和 gmon 文件。

## 当前热点摘要

2026-07-03 本地 5000 轮 profiling 的 `profiling/rmdb_gprof.txt` 顶部 flat profile 显示：

```text
 9.45%  ast::SemValue::~SemValue()
 9.45%  yyparse()
 9.45%  BufferPoolManager::BufferPoolManager(unsigned long, DiskManager*)
 7.87%  yyerror(YYLTYPE*, char const*)
 3.94%  yylex(ast::SemValue*, YYLTYPE*)
 3.94%  QlManager::select_from(...)
 3.15%  Analyze::analyze_select(...)
 2.36%  EnsureStatementTransaction(...)
 2.36%  BufferPoolManager::fetch_page(PageId)
 2.36%  Portal::start(...)
```

初步观察：

- parser/lexer 和 AST 构造析构仍是短事务高频 SQL 的主要 CPU 成本；`src/rmdb.cpp` 还用全局 `buffer_mutex` 串行化解析，高并发下会限制扩展性。
- `QlManager::select_from()` 在 `set output_file off` 后仍会格式化 SELECT 结果返回 socket；点查多时输出路径会成为可见开销。
- `BufferPoolManager::BufferPoolManager()` 仍在采样中占比高，主要来自启动期一次性分配并清零大量 `Page`。评估执行期热点时应排除启动成本。
- `BufferPoolManager::fetch_page()`、`LRUReplacer::pin/unpin()` 和索引扫描函数进入热点，说明页表/LRU 哈希操作和索引游标仍有优化空间。
- `RmScan` 构造时会 `snapshot_rids()` 并排序全表 RID；在非索引扫描、聚合和范围场景中会放大内存分配和共享锁持有时间。

## 并发压测观察

使用 Release 构建和 1/4/8/16 个 socket 客户端对同一组热点行执行 serializable NewOrder 风格事务。服务端未崩溃，未出现 failure 或连接错误，但 abort 比例随并发快速升高：

```text
clients=1   ok=60  abort=0    abort_rate=0.0%
clients=4   ok=60  abort=180  abort_rate=75.0%
clients=8   ok=81  abort=399  abort_rate=83.1%
clients=16  ok=80  abort=880  abort_rate=91.7%
```

当前 `LockManager` 是 no-wait 2PL，遇到冲突直接抛 `DEADLOCK_PREVENTION` abort。在热点行更新场景下，吞吐和成功率会高度依赖线程调度，是性能波动的主要来源之一。

## 注意事项

- 这版不是 `perf` 调用栈采样火焰图，而是 `gprof` flat profile 转换出的 SVG，可用于粗粒度定位热点，但不适合精确判断完整调用链归因。
- `build-profile/` 和 `profiling/` 是本地生成产物，目前未纳入正式源码结构；如需保留，可后续决定是否加入 `.gitignore` 或提交脚本/文档。
- 若后续环境允许 `perf`，建议再用真实调用栈采样生成一版标准 FlameGraph，并与本次结果交叉对比。
